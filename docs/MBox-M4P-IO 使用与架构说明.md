# MBox-M4P-IO 使用与架构说明

> **文档版本**：v1.1（对应 5 键 → 流媒体页面切换版本；v1.1 增补 2.6「按键检测原理 / 上下拉」）
> **硬件平台**：ESP32 DevKit V1（esp32doit-devkit-v1）+ SN65HVD230 3.3V CAN 模块 + 8 路独立按键板（只用 S1~S5）
> **开发环境**：PlatformIO（platform espressif32 7.0.1 / framework-arduinoespressif32 3.20017）
> **构建状态**：`pio run` 编译通过，RAM 6.7%（21840 / 327680 B），Flash 21.6%（282797 / 1310720 B）

## 1. 项目概述

### 1.1 一句话业务

按一下按键板上的 S1~S5，本板通过 CAN（500 kbps）发送 `0x24` 报文里的「流媒体显示切换」信号
（`B3 = 0x41 ~ 0x45`），让 MBox 在 **5 种四画面布局** 之间切换。

```
按键按下 → 消抖确认 → 组装 0x24 帧 → ESP32 TWAI → SN65HVD230 → CAN 总线 → MBox 切页面
```

### 1.2 功能清单

| 编号 | 功能 | 说明 |
|---|---|---|
| F1 | 5 路按键扫描 | 内部上拉 + 25ms 时间消抖 + 边沿事件（按下 / 松开），5ms 扫描节拍，全程无 `delay()` |
| F2 | 按键 → 报文映射 | 映射表集中在 `src/app/KeyCanMap.h`，一行一个按键，改报文只改这一个文件 |
| F3 | 页面绝对直选 | 5 个键 = 5 个页面值，按哪个到哪个，不依赖"当前在第几页"，不会因丢帧而永久错位 |
| F4 | 抗丢帧 | 每次按下连发 3 帧（间隔 20ms），补发在 `tick()` 里非阻塞推进 |
| F5 | 连按抑制 | 同一个键 300ms 内重复确认按下只算一次（机械抖动 / 手指重按） |
| F6 | 页面互斥 | 两个键几乎同时按下时，只认最后按下的，旧键未发完的补发帧作废 |
| F7 | 状态可观测 | 串口逐帧打印报文内容 + `p` 命令打印统计 + `t` 命令打印映射表 |
| F8 | 链路自愈 | CAN 控制器 bus-off 后每 100ms 巡检一次并自动恢复 |
| F9 | 无按键板也能验 | 串口 `k1~k5` 模拟按键，报文与真实按键完全一致 |

### 1.3 本工程不做什么

- **不做翻页式切换**（"上一页 / 下一页"）：协议里 `0x41~0x45` 是绝对值，且 `0x15` 回传报文里
  没有"当前流媒体页面"字段，读不回真实状态 —— 一旦丢帧或用户在 MBox 上手点屏幕，翻页方案会永久错位。
- **不做上电发帧**：MBox 上电默认就是 `0x41`，本板上电**一帧都不发**，不去改动任何页面。
- **不做长按连发**：页面是幂等的绝对量，按住狂发没有意义，还会和 MBox 本地操作打架。
- **不解析接收报文**：`can/CanBits.h` 已具备位域解析能力，但当前业务只发不收。

| 按键板引脚 | 接到 ESP32 | 说明 |
|---|---|---|

### 2.4 引脚选型说明

| 引脚 | 为什么选它 / 注意点 |
|---|---|
| GPIO4 / GPIO5 | TWAI 默认可用脚，已避开所有 strapping 脚 |
| GPIO13 / 14 / 18 / 21 | 均带内部上拉、非 strapping 脚、不占 Flash(6-11) / UART0(1,3) / CAN(4,5) |
| GPIO19 | 带内部上拉，可用；**`platformio.ini` 里把 GPIO19 注释预留给了蜂鸣器**，若以后要加蜂鸣器，把 S4 改到 GPIO23（只改 `BoardPins.h` 一行） |
| GPIO21 | I2C 默认 SDA，本工程未启用 I2C，可放心占用 |
| GPIO22 / 23 / 25 | 本工程**不再使用**（S6~S8 不接线）；GPIO22 注释里预留给了 WS2812 灯带 |

> **不要用**：GPIO6~11（接 Flash，一碰就重启）、GPIO1/3（UART0 日志口）、GPIO0/2/12/15（strapping 脚，影响启动模式）。
>
> **内部上拉可用性**（本工程 `KEY_COM_TO_GND=1` 完全依赖它）：ESP32 的 `GPIO0~GPIO33` 都能配置内部上拉/下拉
> （规格书典型值 ≈45kΩ），所以 GPIO13/14/18/19/21 **不接任何外部电阻也能稳定读键**；
> 但 `GPIO34~GPIO39` 是**纯输入脚、没有内部上下拉**，以后扩键千万不要选这几个脚（原理详见 2.6）。

### 2.5 上电前检查清单

1. 模块 `3.3U` 与 ESP32 `3V3` 相连（**不是 5V**）；
2. 模块 `GND` 与 ESP32 `GND` 相连（共地）；
3. `CAN_TX(D) → GPIO5`、`CAN_RX(R) → GPIO4`，**没有接反**（接反的现象是发送永远失败、TEC 飙升）；
4. 总线未上电时量 `CANH-CANL` 电阻：60Ω（两端各 120Ω）或 120Ω（仅一端）；
5. 按键板 `COM` 接 **GND**，S1~S5 分别接 GPIO13/14/18/19/21；
6. 按一下按键，用万用表量对应 GPIO 与 GND 应导通（< 1Ω）。

### 2.6 按键检测原理：上下拉到底是谁做的？

**结论**：上下拉由 **ESP32 芯片内部**提供（`pinMode(INPUT_PULLUP)`，典型 ≈45 kΩ 接到 3V3）；
按键板是**纯机械开关**（没有电阻、不需要 VCC），它只负责把 GPIO「短接到 GND」。
所以是：**内部上拉负责"平时是高电平"，按键负责"按下时把它拉到地"。**

#### 2.6.1 等效电路

```
                      ESP32 芯片内部                        外部
              ┌──────────────────────────┐
      3V3 ────┤ 内部上拉电阻 ~45kΩ       │
              │         │                │
              │         ├──► 输入缓冲器 ──┼──► digitalRead()
   GPIO13 ────┼─────────┘                │
              └──────────────────────────┘
                        │
                        │  杜邦线
                     ┌──┴──┐
                     │ 按键 │  常开（松开时断开）
                     └──┬──┘
                        │
      按键板 COM ────────┴──── GND ──── ESP32 GND（必须共地）
```

#### 2.6.2 两种状态下的电平与电流

| 状态 | 电路情况 | GPIO 电平 | `digitalRead()` | 流过按键的电流 |
|---|---|---|---|---|
| **松开** | 开关断开，只有 45kΩ 上拉到 3V3 | ≈3.3V | `HIGH` | ≈0（仅输入漏电，nA 级） |
| **按下** | 开关闭合，GPIO 直接短到 GND | ≈0V | `LOW` | 3.3V ÷ 45kΩ ≈ **73 µA** |

- 这就是 **"低电平有效（active-low）"** 接法：`按下 = LOW`、`松开 = HIGH`，与 2.2 的逻辑约定一致。
- 73 µA 由内部上拉电阻限流，**不会烧 IO** —— 因为此时 GPIO 是**输入（高阻）**，不是输出。
- 因为按键板没有电阻，`COM` **必须接 GND**；若把 `COM` 接到 3V3，按键按下时两端都是高电平，等于没接（见 2.6.5）。

#### 2.6.3 代码里就这两行（原理的实现）

```cpp
// src/input/KeyPad.cpp:28 —— 上下拉是在这里"打开"的，不是靠硬件电阻
pinMode(_pins[i], _activeLow ? INPUT_PULLUP : INPUT_PULLDOWN);

// src/input/KeyPad.cpp:63 —— 读电平，按有效电平取反
const bool pressed = (_activeLow ? digitalRead(_pins[i]) == LOW    // 上拉接法：LOW  = 按下
                                 : digitalRead(_pins[i]) == HIGH);  // 下拉接法：HIGH = 按下
```

`_activeLow` 来自 `KEY_COM_TO_GND`（`main.cpp` 里 `keyPad.begin(KEY_PINS, KEY_COUNT, KEY_COM_TO_GND != 0)`）：

| `KEY_COM_TO_GND` | `pinMode` | `COM` 接到 | 松开时 | 按下时 |
|---|---|---|---|---|
| `1`（当前默认） | `INPUT_PULLUP`（~45k 到 3V3） | **GND** | `HIGH` | **`LOW`** |
| `0` | `INPUT_PULLDOWN`（~45k 到 GND） | 3V3 | `LOW` | **`HIGH`** |

> 从"电平变化"到"发出一帧 CAN"，中间还有 5ms 采样节拍 + 25ms 时间消抖 + 边沿判定，
> 完整链路见 5.3 的数据流。

#### 2.6.4 什么情况下必须加外部电阻

内部上拉是**弱上拉**（几十 kΩ、73 µA 湿电流），下列场景建议外接元件：

| 场景 | 现象 | 建议 |
|---|---|---|
| 按键线较长（> 30cm）或走线在强干扰环境 | 偶发误触发：车体振动 + EMI 把浮空段拉低 | 每个 GPIO 加 **4.7kΩ~10kΩ 上拉到 3V3**（与内部上拉并联，等效 ~4kΩ，抗扰显著提升） |
| 触点氧化 / 非镀金触点 | "有时灵有时不灵"、要用力按 | 外部上拉把湿电流从 73 µA 提高到 ~0.7 mA，可击穿氧化膜；或换镀金触点按键板 |
| 长线 + 强干扰同时存在 | 抖动窗口超过 25ms | 外部上拉 + GPIO 对地并 **100nF**（RC ≈ 10kΩ×100nF = 1ms），`KEY_DEBOUNCE_MS` 保持 25ms 即可 |
| 需要更低功耗（电池供电） | 内部上拉在部分低功耗状态下仍耗电 | 外部上拉 + 代码改 `INPUT`（关内部上拉），必要时配 `ext0/ext1` 深睡唤醒 |

> 本工程当前是**短杜邦线 + 台架/车内近距离**用法，内部上拉完全够用，
> 因此 **不加任何外部电阻**：少 5 个焊点、少一处故障点。

#### 2.6.5 四个常见坑

| 坑 | 现象 | 正确做法 |
|---|---|---|
| `COM` 误接 3V3，而代码仍是内部上拉 | 按下时两端都是高电平 → **完全没反应**（CAN 一帧都不发） | `COM` 接 **GND**；或改 `-DKEY_COM_TO_GND=0` 后把 `COM` 接 3V3 |
| 忘记配内部上拉（引脚浮空） | **没按也乱触发**，开机就乱切页面 | 本工程由 `KeyPad::begin()` 统一 `pinMode(INPUT_PULLUP)`，不要自己再改这些引脚模式 |
| 把 GPIO 配成输出且输出 HIGH 时按下 | 3V3 直接对地短路 → 烧 IO / 拉塌电源 | 这些引脚**只用输入模式**，本工程全程不驱动 |
| 扩键时选了 GPIO34~39 | 这几个脚**没有内部上下拉**，读值不定 | 扩键只从 `GPIO0~GPIO33` 里挑非 strapping、非 Flash、非 UART0 的脚 |

> 想亲眼验证：把板子上电后用万用表量 GPIO13 对 GND —— 松开约 **3.3V**，按下约 **0V**；
> 或者用 6.4 的 `KEY_PIN_SCAN=1` 模式看 `[SCAN] S1 -> GPIO13 = LOW(按下)`。

## 3. CAN 协议

> 出处：《机车 CAN 协议公版（对外释放客户）》表格中 `0x24` 报文段。

### 3.1 总线参数

| 项目 | 值 |
|---|---|
| 波特率 | **500 kbps**（`-DCAN_BAUD=500000`） |
| 终端电阻 | 120Ω（总线两端各一个） |
| 帧类型 | **标准帧（11bit）**，`Msg Name = 0x24` |
| DLC | 8 |
| 协议规定周期 | 100 ms（本工程默认不周期发送，见 4.4） |
| 方向 | **R = ADAS 接收**（本板发送 → MBox / 记录仪接收） |
| 本板工作模式 | `CAN_MODE=0` = NORMAL（总线上必须有其它节点回 ACK） |

### 3.2 0x24 报文全信号一览

**一条 `0x24` 帧里打包了 12 个控制信号**，本工程只用 `B3`，其余必须填 `0x00`：

| 字节 | 位 | 长度 | 信号 | 取值含义 | 本工程发送值 |
|---|---|---|---|---|---|
| B0 | B0.0~B0.2 | 3 | 录像控制 | `0x0` 无效(发无效时执行当前状态) / `0x1` 普通录像 / `0x2` 紧急录制(紧急事件唯一触发源) / `0x3` 哨兵模式 / `0x4` 停止录制 | `0x0` |
| B0 | B0.3~B0.5 | 3 | 拍照控制 | `0x0` 无效 / `0x1` 普通拍照 / `0x2` 紧急拍照 | `0x0` |
| B0 | **B0.6** | 1 | **can总线控制** | `0x0` 总线激活(默认) / **`0x1` 总线静默** | `0x0` ⚠️ 绝不能填 1 |
| B1 | B1.0~B1.1 | 2 | 盲区预警 BSD 开关 | `0x0` 无效 / `0x1` 关闭 / `0x2` 打开 | `0x0` |
| B1 | B1.2~B1.3 | 2 | 变道预警 LCW 开关 | 同上 | `0x0` |
| B1 | B1.4~B1.5 | 2 | 后车预警 RCW 开关 | 同上 | `0x0` |
| B1 | B1.6~B1.7 | 2 | 前车预警 FCW 开关 | 同上 | `0x0` |
| B2 | **B2.0** | 1 | **主机复位（恢复出厂设置）** | `0x0` 无效 / `0x1` 复位重启（**需连续 3 帧**） | `0x0` ⚠️ |
| B2 | B2.1 | 1 | 上下电提醒 | `0x0` 上电 / `0x1` 下电提醒 | `0x0` |
| B2 | **B2.2** | 1 | **主机重启** | `0x0` 无效 / `0x1` 重启 | `0x0` ⚠️ |
| B2 | B2.3~B2.4 | 2 | wifi 开关 | `0x0` 无效 / `0x1` 关闭 / `0x2` 打开 | `0x0` |
| B2 | **B2.5** | 1 | **格式化（录像文件清空）** | `0x0` 无效 / `0x1` 格式化 | `0x0` ⚠️ |
| **B3** | **B3.0~B3.7** | **8** | **流媒体显示切换**（目前仅 MBox 支持） | 见 3.3 取值表，范围 0~69 | **`0x41`~`0x45`** |
| B4~B7 | — | — | 未定义 | — | `0x00` |

> 字节序：`Motorola LSB`；`B3` 信号起始位 `B3.0`、长度 8bit、结束位 `B3.7` —— 即**整个字节对齐**，
> 直接把目标值写进 `data[3]` 即可，不需要移位。

|---|---|---|

| `0x1` | 后向实时 | 无（预留） |
| `0x2` | 前向实时 | 无（预留） |
| `0x3` | 中向实时 | 无 |
| `0x4` | 左侧实时 | 无 |
| `0x5` | 右侧实时 | 无 |
| `0x21` | 后向为主背景，前后双小图 | 无（预留） |
| `0x22` | 前向为主背景，前后双小图 | 无 |
| `0x31` | 后向为主背，前中后三小图 | 无 |
| `0x32` | 前向为主背景，前中后三小图 | 无 |
| `0x33` | 中向为主背景，前中后三小图 | 无 |
| **`0x41`** | 后向为主背景，前左右侧三小图 | **S1** |
| **`0x42`** | 前向为主背景，后左右侧三小图 | **S2** |

| **`0x45`** | 组合页面，四图平铺 | **S5** |

### 3.4 本工程实际发送的 5 帧

| 按键 | 名称 | CAN ID | 帧类型 | DLC | Data0 | Data1 | Data2 | **Data3** | Data4~7 |
|---|---|---|---|---|---|---|---|---|---|
| S1 | 后向为主 + 前左右三小图 | `0x24` | 标准帧 | 8 | `00` | `00` | `00` | **`41`** | `00` |
| S2 | 前向为主 + 后左右三小图 | `0x24` | 标准帧 | 8 | `00` | `00` | `00` | **`42`** | `00` |
| S3 | 左侧为主 + 前后右三小图 | `0x24` | 标准帧 | 8 | `00` | `00` | `00` | **`43`** | `00` |
| S4 | 右侧为主 + 前后左三小图 | `0x24` | 标准帧 | 8 | `00` | `00` | `00` | **`44`** | `00` |
| S5 | 组合页面 + 四图平铺 | `0x24` | 标准帧 | 8 | `00` | `00` | `00` | **`45`** | `00` |

报文示例（按 S2）：

```
ID = 0x024（标准帧，11bit）  DLC = 8
Data = 00 00 00 42 00 00 00 00
         │  │  │  │  └── B4~B7 未定义
         │  │  │  └───── B3 = 流媒体显示切换 = 0x42（前向为主 + 后左右三小图）
         │  │  └──────── B2 = 0x00：不复位 / 不重启 / 不格式化 / wifi 无效 / 上电态
         │  └─────────── B1 = 0x00：BSD / LCW / RCW / FCW 全部"无效"
         └────────────── B0 = 0x00：录像无效 / 拍照无效 / 总线激活(不是静默)
```

### 3.5 安全红线（改表时必读）

`0x24` 是同一条帧打包多个控制信号，**除了 B3 之外任何一位填错，都可能造成严重后果**：

| 填错的位置 | 后果 |
|---|---|
| `B0.6 = 1` | MBox **总线静默**，整个节点从总线上"消失"，页面/预警全部失效 |
| `B2.0 = 1`（连续 3 帧） | MBox **恢复出厂设置**，用户配置全部丢失 |
| `B2.2 = 1` | MBox **重启** |
| `B2.5 = 1` | **格式化录像卡**，录像文件全部清空 |
| `B0.0~B0.2 = 0x4` | 停止录像 |

因此 `KeyCanMap.h` 里 5 行的 `data[0] / data[1] / data[2]` **必须全部是 `0x00`**，
只允许改 `data[3]`。这也是为什么每次按键都发"整帧 8 字节"而不是"只发一个字节"。

## 4. 工作流

### 4.1 上电流程

```
上电 / 复位
  │
  ├─ Serial.begin(115200) → 延时 300ms → 打印 "===== MBox-M4P-IO 启动 ====="
  ├─ 打印芯片型号 / 核心数 / Flash 大小
  │
  ├─ canBus.begin()          500 kbps，NORMAL 模式，TX=GPIO5 RX=GPIO4，TX 队列 8 / RX 队列 32
  │    └─ 失败时打印 "[App] CAN 初始化失败：按键报文无法发送，请检查模块接线"，按键扫描仍照常运行
  │
  ├─ keyPad.begin(KEY_PINS, KEY_COUNT, comToGnd)   配置内部上拉并【记录初始电平】
  │    └─ 上电时就已按住的键不会补发"按下"事件（避免上电瞬间误切页面）
  │
  ├─ keyCanBusiness.begin(&keyPad)                 打印映射表 + 发送策略
  ├─ keyPad.onEvent(...)                           绑定 按键事件 → KeyCanBusiness
  │
  └─ 打印串口命令提示 → 进入 loop()
        ★ 此时此刻不会发送任何 CAN 帧，MBox 保持它自己的默认页面（通常就是 0x41）
```

### 4.2 主循环分工

`loop()` 每轮按固定顺序调用 4 个模块，**全部非阻塞，没有一处 `delay()`**：

| 顺序 | 调用 | 周期 / 门限 | 干什么 |
|---|---|---|---|
| 1 | `canBus.poll()` | 每次 loop | 排空接收队列（触发 `onFrame` 回调）+ 每 100ms 巡检一次总线健康（TEC/REC/bus-off，自动恢复） |
| 2 | `keyPad.poll()` | 内部 5ms 门限 | 读 5 路电平 → 时间消抖 → 产生 PRESS / RELEASE 事件 → 调 `onEvent` 回调 |
| 3 | `keyCanBusiness.tick()` | 每次 loop | 推进补发帧（第 2、3 帧）、HOLD_REPEAT 长按连发、空闲保活帧 |
| 4 | `handleSerialCommand()` | 每次 loop | 解析串口命令 `k1~k5` / `p` / `t` |

> 为什么补发帧放 `tick()` 而不用 `delay(20)`：`delay()` 期间按键不扫描、接收不排空，
> 20ms × 3 帧会让按键响应整体变慢。现在"按下确认 → 第 1 帧"是**同一个 loop 内完成**（0 延迟）。

### 4.3 一次按键的完整流程（以 S2 为例）

```
t=0ms     手指按下 S2（GPIO14 被拉到 GND，LOW）
          │
t≈0~5ms   keyPad.poll() 采到电平变化 → 进入"变化候选"状态
          │
t≈25ms    仍为 LOW → 消抖通过 → 产生 PRESS 事件（KEY_DEBOUNCE_MS = 25）
          │   ↳ 若这 25ms 内又弹回 HIGH → 判为抖动，忽略（不产生任何事件）
          │
           KeyCanBusiness::onKeyEvent(PRESS, S2)
          │   ├─ ① 连按抑制：距上次确认按下 < 300ms → 打印"连按抑制"并直接返回
          │   ├─ ② 页面互斥：若有其它页面键还在补发 → 作废其未发帧
          │   ├─ ③ 记录 _lastIndex = 1（供 p 命令查询"最近页面"）
          │   └─ ④ 立即发第 1 帧 + 安排补发 2 帧（_pendingLeft = 2）
          │
t=0ms     【第 1 帧】0x24 [00 00 00 42 00 00 00 00] → "发送成功"
          │
t=20ms    tick() 推进 → 【第 2 帧】同内容
t=40ms    tick() 推进 → 【第 3 帧】同内容，_pendingLeft 归 0（此后不再发）
          │
t≈86ms    松开 S2 → 消抖 25ms → RELEASE 事件
              ↳ KeySendMode::PRESS_ONLY：松开【不发送】任何帧
              ↳ 只打印一行日志 "松开（按住 86 ms）"
```

MBox 视角：收到第 1 帧就已经切到 `0x42`；第 2、3 帧是同一个值，重复执行无副作用（**幂等**）。
即使总线丢了 2 帧中的 1 帧，页面仍然正确。

### 4.4 发送策略与可调参数

| 参数宏 | 默认值 | 作用 | 调大/调小的效果 |
|---|---|---|---|
| `KEY_TX_REPEAT` | `3` | 每次按下总共发几帧 | 1 = 只发 1 帧（最省总线，抗丢帧差）；5 = 更稳但总线占用更多 |
| `KEY_TX_REPEAT_GAP_MS` | `20` | 相邻两帧间隔 | 10 = 更快发完；50 = 更分散 |
| `KEY_PAGE_MUTEX_MS` | `300` | 同一键连按抑制窗口 | 调大 = 更不容易因抖动重复触发，但快速"点两下"也只算一次 |
| `CAN_CTRL_KEEPALIVE_MS` | `0` | 空闲保活帧周期；`0` = 关闭 | 若 MBox 侧要求 `0x24` 必须 100ms 周期在线 → 设 `100`（保活帧 `B3=0x00` = 保持当前显示，不会翻页） |
| `KeySendMode` | `PRESS_ONLY` | 发送时机 | `HOLD_REPEAT` + `repeat_ms` 才会长按连发（页面切换不需要） |

**为什么是"3 帧"而不是"周期 100ms 一直发"**：
协议规定该报文 100ms 周期，那是给"录像/拍照/预警开关"这类需要持续在线状态的信号用的。
页面切换是**一次性、幂等**的绝对量，周期性刷 `0x41` 反而会把用户刚在 MBox 屏幕上手动切走的页面又拽回来。
3 帧覆盖"偶发单帧错误"，又不干扰人工操作，是两者之间的最佳折中。

### 4.5 边界情况行为约定

| 场景 | 行为 | 原因 |
|---|---|---|
| 按键抖动（5~20ms 接触不良） | 不产生事件 | 25ms 时间消抖 |
| 快速连按同一个键 2 次（间隔 < 300ms） | 只发一次（日志提示"连按抑制"） | 重复的绝对量没有意义 |
| 两个键几乎同时按下（< 60ms 内） | 只认最后按下的，前一个未发完的帧作废 | 否则 MBox 可能停在前一个键的页面 |
| 按下后一直按住 | 只发 3 帧，不重复 | `PRESS_ONLY` 模式 |
| 上电时就按住某键 | 不产生按下事件 | `KeyPad::begin()` 记录初始电平 |
| 总线上没有其它节点（无 ACK） | 日志出现"发送失败"，TEC 上升到 128 后 bus-off，随后自动恢复 | `CAN_MODE=0` 需要 ACK；台架自测请改 `CAN_MODE=1` |
| CAN 初始化失败 | 按键仍扫描、日志照打，只是每帧都"发送失败" | 便于在现场区分"按键问题"与"CAN 问题" |
| 连续按不同键（如 S1→S2→S3） | 每次都正常发 3 帧（互斥只影响"未发完的旧键帧"） | 顺序操作是最常见用法 |

设计原则：
- **`app` 层不知道 GPIO 号**，`can` 层不知道有几个按键 —— 换引脚不改业务，换报文不改驱动。

- **`config/BoardPins.h` 是唯一的"可调面板"**，`platformio.ini` 里的 `-D` 宏可覆盖它（现场不改源码也能调参）。

### 5.3 数据流

```
按键物理动作
   │
   ▼ GPIO13/14/18/19/21 电平变化（内部上拉，按下 = LOW）

   │

   │
   ▼ KeyCanBusiness::onKeyEvent()
   │      ├─ 同一键 300ms 内重复？ → 丢弃
   │      ├─ 其它键补发未完成？   → 作废
   │      └─ _press(index)
   ▼ kKeyActions[index]（src/app/KeyCanMap.h）
   │

   │
   ▼ 串口每帧打印一行："[KEY] S2 ... 按下 → ID=0x024 标准帧 DLC=8 [...] 发送成功"
```

### 5.5 `KeyAction` 结构 = 一行一个按键

```cpp
struct KeyAction {
    const char* name;            // 日志用名称（出现在 "[KEY] xxx 按下 → ..."）
    uint32_t    id;              // CAN ID：本工程 0x24
    bool        extended;        // false = 11bit 标准帧，true = 29bit 扩展帧
    uint8_t     dlc;             // 数据长度，本工程 8
    uint8_t     data[8];         // 按下时发送的 8 字节（data[3] = B3）
    KeySendMode mode;            // PRESS_ONLY / PRESS_RELEASE / HOLD_REPEAT
    uint16_t    repeat_ms;       // 仅 HOLD_REPEAT：连发周期（0 按 100ms）
    uint8_t     releaseData[8];  // 仅 PRESS_RELEASE：松开时发送的数据
};
```

`KeySendMode` 三种语义：

| 模式 | 行为 | 本工程用法 |
|---|---|---|
| `PRESS_ONLY` | 按下连发 `KEY_TX_REPEAT` 帧，松开不发 | **5 个页面键全部用这个** |
| `PRESS_RELEASE` | 按下发 `data`，松开发 `releaseData` | 预留（如"按住说话/对讲"类信号） |
| `HOLD_REPEAT` | 按下发一帧，按住期间每 `repeat_ms` 再发一帧 | 预留（如音量+/−） |

`KeyCanMap.h` 末尾有编译期断言，**表行数与 `KEY_COUNT` 不一致会直接编译失败**：

```cpp
static_assert(sizeof(kKeyActions) / sizeof(kKeyActions[0]) == KEY_COUNT,
              "KeyCanMap.h 的报文表行数必须等于 BoardPins.h 中的 KEY_COUNT");
```

**加一个按键的三步（例：S6 接 GPIO23，切到"后向实时 0x1"）**

1. `src/config/BoardPins.h`：`KEY_COUNT` 改成 `6`，`KEY_PINS[]` 末尾加 `23`；
2. `src/app/KeyCanMap.h`：表里加一行
   ```cpp
   { "S6 后向实时", 0x24, false, 8, { 0x00, 0x00, 0x00, 0x01, 0, 0, 0, 0 }, KeySendMode::PRESS_ONLY, 0, { 0 } },
   ```
3. `platformio.ini` 不用改 —— `KEY_COUNT` 只在 `BoardPins.h` 里定义，而且**没有 `#ifndef` 保护**，
   用 `-DKEY_COUNT=6` 会触发宏重定义，必须直接改 `BoardPins.h`。

不需要改 `KeyPad` / `CanBus` / `KeyCanBusiness` / `main.cpp`：
串口 `k6` 命令、`t` 打印表、启动日志里的按键列表都会自动跟上。

### 5.6 关键设计决策与理由

| 决策 | 理由 |
|---|---|
| **绝对寻址直选，不做翻页** | 协议 B3 是绝对值；接收侧 `0x15` 没有"当前页面"字段，翻页方案丢一帧就永久错位 |
| **上电不发帧** | MBox 上电默认就是 `0x41`；本板只在人按键时才动作，避免与主机初始化流程打架 |
| **每次发整帧 8 字节** | CAN 帧必须整帧发送；同时用 `data[0..2] = 0x00`（无效/执行当前状态）确保不误触发其它控制 |
| **连发 3 帧而非 1 帧** | 单帧被总线错误/仲裁挤掉时页面不切；3 帧覆盖偶发丢帧，且值相同（幂等）无副作用 |
| **补发放 `tick()` 不用 `delay()`** | `delay(20)` 会让按键不扫描、接收不排空；非阻塞推进让"按下→发帧"零延迟 |
| **按下发、松开不发（`PRESS_ONLY`）** | 页面切换是瞬时动作，松开时发"回退"值会莫名跳页 |
| **同一键 300ms 连按抑制** | 机械抖动二次确认 / 手指重按会让同一页面帧重复发，抑制窗口让行为更确定 |
| **同报文页面互斥** | 双键同时按下时，两个键的补发帧交错发送会让 MBox 停在旧键的页面 |
| **保活帧默认关闭** | 保活帧 `B3=0x00` 虽不翻页，但上电就周期占总线没必要；MBox 若强制要求再打开 |
| **bus-off 自动恢复** | 现场振动/线束干扰偶发 bus-off，100ms 巡检自动恢复，无需人工复位 |
| **TX 队列 8 帧** | ESP32 默认只有 5，连按几下就满；`txFailed` 会飙高 |

### 5.7 已知限制与扩展方向

| 限制 | 说明 / 后续做法 |
|---|---|
| 只发不收 | `CanBus` 已支持接收回调、`CanBits` 已支持位域解析，但业务层未对接；将来要读 `0x15` 状态帧（车速/转向等）再补 |
| 整帧覆盖式发送 | 以后若要同时支持"录像/拍照/BSD 开关"等键，必须引入**影子帧**（保存各信号当前值，发送前合成整帧），否则按键会互相清零 |
| 未接入文件系统 / OTA | `partitions.csv` 预留了 OTA + LittleFS（1.44MB），当前未使用 |
| 策略参数不可现场调 | `KEY_TX_REPEAT` 等是编译期宏；如需现场可调可加 NVS 存储 |
| 串口日志常开 | `_sendAction()` 每帧都打印，约 3.5ms/行 @115200；量产若嫌啰嗦可加编译开关（当前 3 帧共 ~10ms，不影响 20ms 帧间隔） |
| 按键上限 8 路 | `KeyPad::MAX_KEYS = 8`（与 8 路按键板硬件一致）；要更多需改数组维度 |

### 6.3 串口命令

| 命令 | 作用 | 输出样例 |
|---|---|---|
| `k1` ~ `k5` | 模拟对应按键按下（不需按键板） | `[SIM] 模拟 S2 ... 按下` + 3 帧日志 |
| `p` | 打印 CAN 统计 + 最近页面 | 见下 |
| `t` | 重新打印映射表 | 同 6.1 的表 |

`p` 的输出：

```
[CAN] 运行中 | 接收 0 帧 / 发送 3 帧 / 失败 0 次
[CAN] TEC=0 REC=0 bus-off=0 次 接收丢帧=0
[CAN] 尚未收到任何报文
[KEY] 最近页面：S2 前向为主+后左右三小图 → ID=0x024 B3=0x42
```

判断要点：`发送 3 帧 / 失败 0 次` 且 `TEC=0` = 链路正常；`失败 N 次 + TEC 上升` = 无 ACK / 接线问题。

### 6.4 引脚探测模式（首次核对接线用）

打开方式：`platformio.ini` 的 `build_flags` 里取消这一行的注释，重新编译烧录：

```ini
-DKEY_PIN_SCAN=1
```

该模式下的行为差异：

- `setup()` 只调 `keyPad.begin()`，**不调用** `keyCanBusiness.begin()`、不绑定事件 → **完全不会发送任何 CAN 帧**；
- `loop()` 每轮调用 `keyPad.debugScan()`，只在电平**变化**时打印一行：

```
[SCAN] S1 -> GPIO13 = LOW(按下)
[SCAN] S1 -> GPIO13 = HIGH(松开)
[SCAN] S4 -> GPIO19 = LOW(按下)      ← 如果按的是 S2 却打印 S4，说明线序接错
```

用法：按 S1→S2→S3→S4→S5 顺序各按一次，核对打印的 `Sx` 与 `GPIOx` 是否与 2.2 接线表一致。
若某键无任何打印 → 该键 COM 没接到 GND，或 GPIO 接错/虚接。

> 核对完记得把 `-DKEY_PIN_SCAN=1` **重新注释掉**，否则按键不会发 CAN。

### 6.5 台架自测（没有 MBox 也能验证链路）

把 `platformio.ini` 改成：

```ini
-DCAN_MODE=1        ; NO_ACK：发送不需要其它节点回 ACK
```

效果：单板空中发送也会返回"发送成功"，`p` 命令里 `TEC` 不会飙升。
配合 CAN 分析仪可以抓到完整帧，逐字节核对 `00 00 00 41 00 00 00 00`。

注意：
- **NO_ACK 只能单机台架用**，接进真实总线会干扰其它节点（它不按正常 ACK/错误规则行事）；
- `CanBus::transmit()` 支持 `selfTest = true`（自发自收回环），但当前业务代码**没有**传该参数；
  若想在本板验证"能发也能收"，可在 `main.cpp` 的 `setup()` 末尾临时加一行测试：
  ```cpp
  uint8_t t[8] = { 0 };
  canBus.onFrame([](const CanFrame& f) {
      Serial.printf("[TEST] 回环收到 ID=0x%03lX DLC=%u [%02X %02X %02X %02X %02X %02X %02X %02X]\n",
                    (unsigned long)f.id, f.dlc, f.data[0], f.data[1], f.data[2], f.data[3],
                    f.data[4], f.data[5], f.data[6], f.data[7]);
  });
  canBus.transmit(0x24, t, 8, false, /*selfTest=*/true);
  ```
- 验证完请把 `-DCAN_MODE` 改回 `0`。

## 8. 故障排查

### 8.1 症状对照表

| 症状 | 最可能原因 | 处理 |
|---|---|---|
| 串口完全没输出 | 波特率不对 / 端口选错 / 板子没上电 | 监视器设 115200；确认 COM 口；按一下 EN |
| 串口乱码 | 监视器波特率不是 115200 | 改成 115200 |
| 按按键**没有任何日志** | 按键板 COM 未接 GND / GPIO 接错 / 用了探测模式 | 用 6.4 的 `KEY_PIN_SCAN=1` 逐个核对接线；确认 `COM → GND` |
| 按按键完全没反应，但接线"看起来对" | `COM` 接到了 **3V3**，而代码仍是内部上拉 → 按下时两端都是高电平 | 把 `COM` 改接 **GND**；或改 `-DKEY_COM_TO_GND=0` 并把 `COM` 接 3V3（见 2.6.5） |
| 没按键也会乱触发 / 开机就乱跳页面 | 引脚浮空（未配内部上拉，或误选了无内部上下拉的 GPIO34~39） | 由 `KeyPad::begin()` 配 `INPUT_PULLUP`；扩键别用 GPIO34~39，必要时加 4.7k 外部上拉（见 2.6.4） |
| 按 S2 打印的却是 S4 的报文 | 按键线序与 `KEY_PINS[]` 不一致 | 用探测模式核对后，改 `BoardPins.h` 的 `KEY_PINS[]` 或重新插线 |
| 日志有"发送成功"但 MBox 不切页 | ID / 字节位置 / 取值与协议不符；或 MBox 未加载 0x24 解析 | 用 CAN 分析仪核对：标准帧、`ID=0x024`、`DLC=8`、`data[3]=0x41~0x45`、其余字节全 `00`、500 kbps |
| 日志"发送失败（已发 0 帧 / 失败 N 次 / TEC=1xx）" | 总线上没有节点回 ACK（`CAN_MODE=0`）→ 台架单机；或 CANH/CANL 接反/未共地 | 台架改 `-DCAN_MODE=1`；实车检查接线、终端电阻、共地 |
| 上电后 MBox 突然重启 / 录制停止 / 卡被格式化 | `0x24` 的 B0/B2 被写入了非 0 值 | 立刻检查 `KeyCanMap.h` 的 `data[0..2]` 是否仍全为 `0x00`（见 3.5 安全红线） |
| 按一次跳两个页面 / 页面来回跳 | 按键机械抖动导致重复确认；或 `KEY_PAGE_MUTEX_MS` 太小 | 把 `-DKEY_PAGE_MUTEX_MS` 调到 `500`；检查按键板接触 |
| 双击同一个键只有第一次有效 | 300ms 连按抑制窗口 | 属预期行为；确需快速连按就调小 `-DKEY_PAGE_MUTEX_MS` |
| 双键同按时页面不是最后按的 | 两键按下间隔超过 60ms，各自都发完了 3 帧 | 属预期行为（按顺序操作即可）；如需严格互斥可加大 `KEY_PAGE_MUTEX_MS` |
| 日志出现"总线 bus-off（TEC=…），开始自动恢复" | 线束干扰 / CANH-CANL 短路 / 波特率不匹配 / 两端共 240Ω | 检查线束与终端电阻（`CANH-CANL` 应为 60Ω 或 120Ω）、确认全网 500 kbps；恢复是自动的 |
| `p` 里 `接收 X 帧` 一直是 0 | 本板只发不收；`onFrame` 未注册 | 正常现象（当前业务不需要接收） |
| `p` 里"最近页面：（尚未按过按键）" | 上电后还没按过任何键 | 正常现象 |
| 烧录报错 `Failed to connect` | 串口被别的程序占用 / 需要手动进下载模式 | 关掉其它串口工具；按住 `BOOT` → 点一下 `EN` → 松开 `BOOT` 再烧 |
| 改了 `KEY_COUNT` 后编译报 static_assert 失败 | `KeyCanMap.h` 表行数与 `KEY_COUNT` 不一致 | 按 5.5 的三步同步修改 |

### 8.2 现场快速判定流程

```
按键按下没反应？
├─ 串口有 [KEY] ... 日志？ ── 否 ──→ 按键/接线问题 → 用 KEY_PIN_SCAN=1 核对接线

```
